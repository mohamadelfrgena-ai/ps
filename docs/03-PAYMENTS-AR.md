# بوابة الدفع الإلكتروني في AddonStation — الشرح الكامل وماذا تفعل

> الوثيقة `AddonStation-Plans-Payments-Spec.md` تنص على أن الأصل هو **تحويل يدوي + إيصال + موافقة الإدارة**، وتذكر أن بوابات الدفع الآلية لم تُعتمد في المرحلة الأولى بسبب قيود الحسابات البنكية في ليبيا.
> لذلك بُنيت المنظومة على **مساري دفع** يعملان معاً بلا تعارض:

| المسار | الحالة | متى تستخدمه |
|---|---|---|
| 1) الدفع اليدوي (تحويل محلي + إيصال + موافقة Admin) | ✅ مبني وجاهز الآن | فوراً، بلا أي حساب تاجر |
| 2) بوابة دفع إلكتروني (Stripe) | 🟡 الكود جاهز — يحتاج حسابك ومفاتيحك | عندما يتوفر لديك حساب Stripe في دولة مدعومة |

---

## 1) المسار الأول: الدفع اليدوي (يعمل اليوم)

### ما يراه المستخدم
1. **الملف الشخصي → خطتي** → يعرض: `{الخطة} مفعّلة 🎉 · تنتهي في {date}` أو `الخطة المجانية 🍃`.
2. يضغط **شراء اشتراك 💳** → تُفتح شاشة **CHECKOUT**:
   - اسم الخطة و`{price} د.ل / {days} يوم` (تُقرأ من الجدول، وإن كانت الخطة موقوفة تظهر: **«الخطة غير متاحة.»**).
   - قائمة **طريقة الدفع** (OnePay / LPay / Edfa3li / MobiCash / Sadad / Tadawul / تحويل مصرفي) — تظهر الطرق **المفعّلة** فقط.
   - زر **إنشاء طلب الدفع**.
3. تظهر شاشة **«طلبك جاهز»**:
   - **رقم الطلب**: `AS-XXXXXXXX`.
   - **اسم المستفيد** و**رقم الحساب/المحفظة** و**تعليمات الإدارة** (مع زر نسخ).
   - يرفع **صورة الإيصال** (PNG/JPEG/WEBP) ويدخل **رقم العملية** ثم **إرسال الإيصال** → **«تم إرسال طلبك للمراجعة ✅»**.
4. **طلباتي**: قائمة بحالة كل طلب (قيد الانتظار / قيد المراجعة / مفعّل / مرفوض + سبب الرفض).

### ما تفعله أنت (Admin)
1. **الإعدادات (لوحة الإدارة) → الخطط والدفع**:
   - عدّل **السعر** و**المدة بالأيام** لكل خطة، و**حد التحميلات** لكل خطة.
   - أضف/عدّل طرق الدفع: الاسم، **اسم المستفيد**، **رقم الحساب/المحفظة**، **التعليمات**، ثم **فعّلها**.
   > الطرق تُشحن **معطّلة** افتراضياً لتضع أنت بياناتك الحقيقية أولاً (نفّذ مثلاً):
   ```sql
   update public.payment_method_settings
      set enabled = true,
          account_name = 'اسمك أو اسم المتجر',
          account_identifier = '091-XXXXXXX',
          instructions = 'حوّل المبلغ ثم ارفع الإيصال ورقم العملية.'
    where code = 'bank_transfer';
   ```
2. **المدفوعات**: تُعرض الطلبات (المستخدم، الخطة، المبلغ، الطريقة، الرقم المرجعي، الحالة) مع أزرار:
   - **عرض الإيصال** (رابط موقّع صالح 60 ثانية).
   - **تأكيد الدفع** → يفعّل الخطة فوراً ويحسب تاريخ الانتهاء.
   - **رفض** (+ سبب يصل للمستخدم كإشعار).

### ماذا يحدث داخلياً عند «تأكيد الدفع» (كله في دالة واحدة)
`approve_payment_order(order_id)` تنفّذ على الخادم:
1. تتأكد أن المنفّذ **Admin** وأن الطلب بحالة `submitted` ولم يُفعّل سابقاً.
2. تضبط `profiles.plan` و`plan_expires_at = (max(now, التاريخ الحالي) + duration_days)` — أي أن **التجديد المبكر يضيف المدة** بدل أن يضيع الباقي.
3. تحوّل حالة الطلب إلى `approved` مع `reviewed_by` و`reviewed_at`.
4. ترسل **إشعاراً** للمستخدم.
5. تكتب سطراً في **سجل العمليات** `admin_audit_log`.

> ملاحظة من الوثيقة §5.3 و§3.3: **المبلغ لا يأتي من الهاتف أبداً** — دالة `create_payment_order` تقرأه من `subscription_plans` وتتجاهل أي مبلغ يرسله التطبيق. والمستخدم لا يستطيع تحويل طلبه إلى `approved` أو تعديل حالته؛ مسموح له فقط `pending → submitted` مرة واحدة وبواسطة الدالة.

## 2) المسار الثاني: بوابة Stripe (عند توفر حسابك)

### قبل أن تبدأ — تنبيه واقعي
Stripe **لا يدعم ليبيا** كدولة للتاجر. للتفعيل تحتاج واحدة من:
- حساب شركة/أفراد في **دولة مدعومة** (الإمارات، السعودية، مصر، تركيا، دول أوروبية، أمريكا...)، أو
- استخدام **Merchant of Record** مثل Paddle / Lemon Squeezy (يبعان نيابة عنك ويسحبان لحسابك)، أو
- بوابة إقليمية: **Paymob** (مصر)، **Tap Payments** (الخليج)، **MyFatoorah**، أو بوابات محلية ليبية مثل **Edfa3li / MobiCash / Sadad / Tadawul / OnePay / LPay** (معظمها يوفّر API تاجر).

الكود المُرفق مكتوب لـ **Stripe** لأنه الأوضح للتوثيق والاختبار، وبنية الربط نفسها تُستخدم مع غيرها.

### الخطوات بالتفصيل

**أ) أنشئ حساب Stripe**
1. https://stripe.com → Sign up → أكمل بيانات النشاط.
2. من لوحة التحكم تأكد أنك في **Test mode** (زر التبديل أعلى اليمين) للتجربة.

**ب) احصل على المفاتيح**
- **Developers → API keys**:
  - `Publishable key` (للواجهة — غير مطلوب هنا).
  - `Secret key` → `sk_test_...` للتجربة و `sk_live_...` للإنتاج. ⛔ لا يوضع في التطبيق أبداً.

**ج) ثبّت Supabase CLI وانشر الدوال**
```bash
# مرة واحدة
npm i -g supabase
supabase login
supabase link --project-ref <project-ref>

# ضع المفاتيح كأسرار (لا تُكتب في الكود)
supabase secrets set STRIPE_SECRET_KEY=sk_test_xxx
supabase secrets set STRIPE_WEBHOOK_SECRET=whsec_xxx
supabase secrets set SITE_SUCCESS_URL="addonstation://payment/success"
supabase secrets set SITE_CANCEL_URL="addonstation://payment/cancel"

# نشر الدوال الموجودة في المودع
supabase functions deploy stripe-checkout
supabase functions deploy stripe-webhook --no-verify-jwt
```

**د) اربط الـ Webhook في Stripe**
- **Developers → Webhooks → Add endpoint**
- Endpoint URL: `https://<project-ref>.supabase.co/functions/v1/stripe-webhook`
- الحدث: **`checkout.session.completed`**
- انسخ **Signing secret** (`whsec_...`) إلى `STRIPE_WEBHOOK_SECRET` أعلاه (أعد تشغيل أمر `secrets set`).

**هـ) فعّل الطريقة في قاعدة البيانات**
```sql
update public.payment_method_settings
   set enabled = true, provider = 'stripe', name = 'Card (Stripe)'
 where code = 'stripe';
```
> بعد هذا ستظهر خيار «Card (Stripe)» في شاشة الدفع. عند اختياره يستدعي التطبيق دالة `stripe-checkout` التي:
> 1. تتحقق من هويتك عبر JWT، 2. تنشئ **طلب دفع** في القاعدة بالمبلغ الصحيح،
> 3. تنشئ **جلسة Checkout** في Stripe، 4. تعيد رابط الدفع لفتحه في المتصفح.
> وعند نجاح الدفع يرسل Stripe حدث **webhook** → تنفّذ دالة `stripe-webhook` الدالة `gateway_confirm_order` فتُفعّل الخطة تلقائياً.

**و) اختبر**
- بطاقة تجريبية: `4242 4242 4242 4242` — أي تاريخ مستقبلي — أي CVC.
- تحقق أن طلب الدفع تحوّل إلى `approved` وأن `profiles.plan` تغيّر.

**ز) للإنتاج:** بدّل المفاتيح إلى `sk_live_*` وأعد ربط الـ Webhook بمفتاح الإنتاج.

### قيود يجب معرفتها
| القيد | التفصيل |
|---|---|
| العملة | Stripe لا يدعم **LYD**؛ الكود يرسل المبلغ بالدولار من `price_usd` (عدّل الأسعار من لوحة الإدارة) |
| Apple/Google Pay | تُفعّل من إعدادات Stripe ثم تعمل تلقائياً داخل Checkout |
| الاسترجاع (Refund) | يجب أن يكون من لوحة Stripe يدوياً، ثم تُلغى الخطة من لوحة الإدارة |

## 3) تحذير Google Play (من الوثيقة §9)

بيع الوصول الرقمي داخل تطبيق منشور على **Google Play** يخضع عادةً لشرط استخدام **Google Play Billing** (مع استثناءات حسب الدولة والبرنامج).
- إن نشرت التطبيق على Google Play → اقرأ سياسة Play Payments الحالية قبل الربط، وقد تحتاج إضافة Play Billing كمسار ثالث.
- إن وزّعت التطبيق كـ **APK خارج المتجر** → لا ينطبق هذا الشرط.

## 5) قائمة الأسئلة التي يجب أن تحسمها ([DECIDE] في الوثيقة §10)

| # | السؤال | القيمة الافتراضية المُنفَّذة حالياً | كيف تغيّرها |
|---|---|---|---|
| 1 | الأسعار والعملة والمدة | Epic = 25 د.ل / 2.99$ · Legendary = 50 د.ل / 5.99$ · 30 يوماً | لوحة الإدارة → الخطط والدفع |
| 2 | حدود التحميل | Free = 5/يوم · Epic = 30/يوم · Legendary = بلا حد | نفس الشاشة (حقل `download_limit`) |
| 3 | أدوات الشات | **Legendary فقط** + أداة الإدارة (حسب توصية الوثيقة) | عدّل `site_assets.required_plan` |
| 4 | الحصريات (Exclusives) | تتبع قاعدة الخطة العادية | `content_items.is_exclusive` + الخطة |
| 5 | فتح محتوى Legendary بالـ AC | مسموح **فقط** إن وضعت أنت سعر AC للعنصر (`ac_price > 0`) | لوحة الإدارة → إضافة/تعديل محتوى |
| 6 | طرق الدفع والأرقام | معطّلة بانتظار بياناتك | لوحة الإدارة → الخطط والدفع |
| 7 | بعد انتهاء الاشتراك | يُحفظ الأفاتار/الأداة لكن يُعرض مقفلاً حتى التجديد | الوثيقة §6 — أبلغني إن أردت التصفير التلقائي |
| 8 | النشر على Google Play | غير محدد | راجع القسم 3 أعلاه |

أخبرني بأي قيمة تريد تغييرها وأعدّلها لك في الكود/القاعدة فوراً.
